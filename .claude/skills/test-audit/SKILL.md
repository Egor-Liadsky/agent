# Аудит тестов

Два режима, одна планка ценности. **Авторский гейт** проверяет каждый новый или
изменённый тест при написании. **Аудит** — сфокусированный обход существующих
тестов в поисках дублей, пересказов кода и привязки к реализации. Цель —
уверенность, а не число удалённых тестов. Широкий аудит дробить на отдельные
связные коммиты по репозиториям.

## Карта тестов проекта

Общего workspace нет: команды выполнять из каталога конкретного репозитория.

| Репозиторий | Где тесты | Как запускать |
|---|---|---|
| `agent-cli` | `#[cfg(test)]` в `crates/core/src/*.rs` (`config`, `pipeline`, `invariants`), `crates/client/src/tests.rs`, `crates/client/src/chats/tests.rs`, `crates/cli/src/*.rs` (`tui.rs` — самый крупный, `mcp.rs`, `tool_loop.rs`) | `cargo test`, точечно `cargo test -p agentcore config::` |
| `agent-sever` | `src/tests.rs` (HTTP через `wiremock`), модульные в `store.rs`, `config.rs`, `memory.rs`, `task.rs`, `summary.rs`, `context.rs`, `app.rs` | `cargo test`, финально `cargo test --locked` |
| `mcp/git`, `mcp/activity`, `mcp/pipeline` | `crates/*/tests/protocol.rs` (запускают собранный бинарник по JSON-RPC) и модульные в `src/` | `cargo test`, `cargo clippy --all-targets -- -D warnings` |
| живые тесты клиента | `#[ignore]`: `live_server`, `live_daemon`, `live_pipeline` | только вручную, см. команды в корневом `CLAUDE.md` |

Первый граничный слой для контракта — тот, что видит внешний потребитель:
HTTP-эндпоинт у `agentd`, JSON-RPC у MCP-серверов, публичный API `agentcore`.
Модульный тест приватной функции — слабее и нужен, только если граница не
достаёт до риска.

## Авторский гейт

Перед добавлением теста ответить на четыре вопроса. Нет ответа — теста пока нет.

1. Какое наблюдаемое поведение, инвариант или независимый контракт он защищает?
2. Какая реальная регрессия его уронит?
3. Почему это не ловит существующий тест? У контракта один основной владелец на
   самой сильной границе. Второй слой оправдан только собственным риском
   (транспорт, жизненный цикл). Вместо почти-дубля — строка в таблице
   параметризованного теста или общая фикстура.
4. Нужен ли seam, который не нужен продакшену: `pub` ради теста,
   `#[cfg(test)]`-ветка в боевом коде, лишний параметр, трейт с одной боевой
   реализацией? Если да — перенести тест на настоящую границу.

Затем сверить с [junk-паттернами](#junk-паттерны). Совпадение проваливает гейт,
если [планка удержания](#планка-удержания) не называет контракт, который тест
охраняет независимо. Тест, ломающийся при рефакторинге без смены поведения,
проверяет реализацию — переписать на владеющей границе.

Регрессионный тест на баг обязан падать на коде до исправления и по тому же
поводу, иначе он проверяет мок, а не починку. Один регрессионный тест на
границе владельца; не повторять сценарий на каждом слое.

## Junk-паттерны

Чек-лист для обоих режимов.

- тесты без утверждений (прогон «для покрытия»);
- сравнение значения с самим собой, копирование конструкции в ожидание;
- ожидание, посчитанное тем же кодом, который тестируется;
- копия констант, списков или манифестов из кода (`assert_eq!(X, "то же самое")`
  без внешнего контракта);
- `include_str!`/grep по исходникам вместо запуска поведения;
- тест приватного предиката или формы вызова, который повторён на реальной
  границе;
- десяток тестов с одним телом и разными входами (`non_numeric_x_is_error`,
  `zero_x_is_error`, …) — сворачивать в таблицу `&[(вход, ожидание)]`;
- дубли одного контракта в разных слоях без собственного риска у каждого;
- `wiremock`/фейк, реализующий то самое поведение, которое проверяется, или
  один одинаковый мок под разные API;
- фикстура, подкладывающая результат, который должен произвести владелец
  (порядок, квитанции, состояние);
- проверка персистентности не в том хранилище, куда путь пишет
  (`store.rs`/SQLite против памяти);
- проверка «поддерживает X» по объявленным флагам вместо самой доставки;
- негативный контроль, проходящий по постороннему поводу: отказ другого
  предохранителя, ошибка, до которой путь не доходит;
- имя обещает больше, чем проверяет вход;
- код, живущий в продакшене только ради тестов.

## Планка удержания

Оставить тест, если он независимо охраняет:

- публичный API `agentcore` или контракт между репозиториями: имена
  инструментов и схемы аргументов (`READ_ONLY_TOOLS`, `CHAT_TOOLS`), поля
  `structuredContent` конвейера, конверт ошибок `agentd`
  `{ "error": { "code", "message", "request_id" } }`;
- конфиг и запуск: фатальность старта при плохой переменной `AGENTD_*`,
  умолчания, маскирование секретов;
- хранилище и миграции (`sqlx`, владелец чата по отпечатку токена);
- безопасность: `save_to_file` только внутри `--output`, отказ на `api_key` в
  теле запроса, отсутствие токенов в БД и логах;
- порядок стадий конвейера, когда порядок наблюдаем;
- регрессию с реальным сценарием отказа;
- проверку по исходнику, если она самая дешёвая независимая и переживает
  переименование идентификатора.

«Медленный» или «статичный» — не причина удалять. Оставленный тест, падающий на
базовой ветке, — возможный баг продукта: воспроизвести и чинить владельца, а не
удалять тест.

## Правила проекта, которые тесты не нарушают

- `agentcore` не зависит от терминала; в `mcp/**/Cargo.toml` нет `agentcore`,
  `agentclient`, `agentupstream`, `agentcli`. Тест не вводит таких зависимостей.
- Ошибки провайдера различаются через `downcast_ref::<AgentError>`, поэтому и
  тест проверяет тип ошибки, а не текст сообщения.
- Тесты `agentd` подменяют провайдера через `wiremock`, а не сетевой доступ.
- Пути к бинарникам MCP в тестах абсолютные (`AGENTCLI_GIT_MCP`,
  `AGENTCLI_PIPELINE_MCP`): `cargo test` идёт из каталога крейта.
- Комментарии и имена в тестах — по общим соглашениям: комментарий объясняет
  выбор, а не пересказывает строку; комментарии на русском.

## Разведка

Только чтение; сначала отчёт с доказательствами, потом правки. Для широкого
охвата идти по полосам: `agent-cli/crates/core`, `agent-cli/crates/client` и
`crates/cli`, `agent-sever`, `mcp/*`, затем сквозной поиск junk-паттернов
(одинаковые тела тестов, `#[cfg(test)] pub`, тесты без `assert`).
Полезные заходы: `grep -c '#\[test\]'` по файлам, чтение всего теста и его
владельца вместе с вызывающими, `git log -- <файл>` для истории. Если тест
утверждает поведение зависимости (`rmcp`, `axum`, `sqlx`), смотреть её исходник
или типы, а не догадываться.

Лучше несколько уверенных кандидатов, чем длинный спекулятивный список.

## Доказательства по кандидату

Пока не заполнено всё, кандидат к правке не готов:

- точное имя и место теста;
- какой сбой он реально способен обнаружить;
- небоевые вызывающие: кто ещё использует seam;
- более сильное доказательство у владельца границы или почему оно не нужно;
- история: зачем тест или seam появились (`git log`, issue или task notes);
- что удаление освобождает в продакшене или тестовой поддержке;
- риск и точная команда проверки.

## Форма правки

Один связный батч на владельца. Сворачивать копипасту в таблицы, удалять
`#[cfg(test)]`-обёртки и мёртвый код, нужный только тестам, вместо сохранения
алиасов. Регрессии переносить на канонического владельца. Предпочитать
отрицательный прирост строк продакшена. Не добавлять взамен новые тесты,
пересказывающие ту же реализацию; неуверенные кандидаты не превращать в
«уборку» ради счётчика.

## Проверка

Из каталога затронутого репозитория:

1. Точечно: `cargo test <фильтр>` для тестов владельца и соседей.
2. Таблицу после сворачивания проверить на выживаемость: временно сломать
   разбор одной переменной или ветки и убедиться, что нужная строка падает.
3. `cargo clippy --all-targets -- -D warnings` (обязательно для `mcp/*`).
4. `git diff --check`, затем `git diff --numstat`; продакшен и тесты сообщать
   раздельно.
5. Если правка меняла ядро `agentcore`, соблюсти порядок из корневого
   `CLAUDE.md`: тесты ядра → пуш `agent-cli` → в `agent-sever` убрать
   `[patch]`, `cargo generate-lockfile`, `cargo test --locked`.
6. Финально прогнать полный `cargo test` репозитория.

Не править файлы, пока в этом же репозитории идёт `cargo test`.

## Коммиты

Коммитить только по разрешению. Каждый подмодуль коммитится из своего каталога
и пушится в свой `origin`; затем в корне зонтика отдельным коммитом
фиксируется новый указатель подмодуля. Сообщение коммита — на английском,
повелительное наклонение («Collapse config error tests into a table»).
README трогать, только если менялось поведение, а не только тесты.

## Итоговый отчёт

- причина и убранные категории низкоценных тестов;
- упрощения в продакшене;
- оставленные ложные срабатывания и чем они ценны;
- реально запущенные проверки: точечные и полные;
- строки продакшена против строк тестов;
- состояние коммитов и пуша по репозиториям;
- названные следующие шаги.
