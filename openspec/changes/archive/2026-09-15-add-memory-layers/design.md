## Context

См. `proposal.md — Why` про мотивацию. Здесь — что уже есть в `agent-sever` и
`agent-cli` и как в это встраивается новая стратегия.

`agent-sever/src/context.rs` — единственная точка ветвления по стратегии:
приватный трейт `ContextStrategyImpl` с методом `assemble`, реализации —
приватные структуры (`SummaryImpl`, `WindowImpl`, `FactsImpl`,
`BranchingImpl`), подбираемые в `impl_for` по значению `ContextStrategy`.
Каждая реализация возвращает `Assembled { history, context: ContextDto,
sections: Vec<String> }` — `sections` вставляются в системное сообщение
функцией `system_message::build` в фиксированном порядке (в порядке, в каком
реализация их вернула), `context` уходит клиенту как блок наблюдаемости.
`FactsImpl` — ближайший прецедент по форме: отдельный дешёвый вызов модели
после ответа (`facts::update_after_exchange`), JSON-массив операций
`{op, key, value}`, разбор терпимый к мусору вокруг JSON
(`parse_operations`), отказ разбора или вызова возвращает `false` и не трогает
хранилище. Это ровно тот приём, который нужен маршрутизатору памяти — новый
код не придумывает свой формат отказа, а переиспользует этот.

`agent-sever/src/store.rs` — таблицы `chats` (колонка `owner` — SHA-256
клиентского токена), `chat_branches`, `messages` (с `branch_id`),
`chat_facts` (составной ключ `(chat_id, key)`), `chat_summaries`. Миграции —
чистый SQL в `migrations/NNNN_*.sql`, применяются `sqlx::migrate!()` при
старте. Новые таблицы памяти следуют тому же стилю: явные внешние ключи,
`ON DELETE CASCADE`, отдельные индексы под фактические запросы.

`agent-sever/src/config.rs` читает только `AGENTD_*`; `ChatSettings` в
`agent-cli/crates/core/src/config.rs` (`agentcore`) — единственное место
клиентских переопределений, попадающее в `POST /v1/chats` и
`PATCH /v1/chats/{id}` через `ChatSettingsDto`. Пятое значение
`ContextStrategy` и новые поля `ChatSettings` — правка ядра, поэтому
подчиняется общему порядку: правка в `agent-cli`, тесты там же, пуш в
`main`, затем в `agent-sever` снятие `[patch]`, `cargo generate-lockfile`,
`cargo test --locked`.

## Goals / Non-Goals

**Goals:**
- Три слоя памяти с раздельным хранением и разной областью жизни, видимые и
  управляемые снаружи (HTTP, TUI).
- Маршрутизация — явное, наблюдаемое решение, переиспользующее приём
  `facts.rs` (отдельный дешёвый вызов, терпимый разбор, отказ не рушит ответ).
- Стратегия `memory_layers` встраивается в `agent-sever/src/context.rs`
  одной веткой `match`, без условий по слоям в `handle_chat_in_existing`.

**Non-Goals:**
- Векторный поиск, эмбеддинги или ранжирование по релевантности записей
  долговременной памяти — выборка в разделе системного сообщения плоская
  (все записи владельца в пределах лимита), без семантического отбора.
- Автоматическое определение начала/конца задачи по содержимому диалога —
  задача в этой версии заводится и завершается явным вызовом (маршрутизатор
  может задать `task_id` операцией, но не создаёт и не закрывает задачу
  implicitly отдельным решением; закрытие задачи — отдельное явное действие,
  см. решение 3).
- Общая память между разными владельцами — долговременная память строго в
  области видимости одного `owner`, как и чаты.

## Decisions

### 1. Схема хранения: две новые таблицы в agent-sever, `messages` не трогаем

`chat_working_memory` — рабочая память, привязана к чату и задаче:

```sql
CREATE TABLE chat_working_memory (
    id          TEXT    PRIMARY KEY,
    chat_id     TEXT    NOT NULL REFERENCES chats (id) ON DELETE CASCADE,
    task_id     TEXT    NOT NULL,
    key         TEXT    NOT NULL,
    value       TEXT    NOT NULL,
    source      TEXT    NOT NULL,   -- 'router' | 'manual'
    updated_at  INTEGER NOT NULL,
    UNIQUE (chat_id, task_id, key)
);
CREATE INDEX chat_working_memory_chat_task ON chat_working_memory (chat_id, task_id);
```

`owner_long_term_memory` — долговременная память, привязана к владельцу, с
необязательной ссылкой на чат-источник (при удалении чата запись остаётся —
это её смысл, «переживает чат», поэтому `ON DELETE SET NULL`, а не `CASCADE`):

```sql
CREATE TABLE owner_long_term_memory (
    id             TEXT    PRIMARY KEY,
    owner          TEXT    NOT NULL,
    entry_type     TEXT    NOT NULL,   -- 'profile' | 'decision' | 'knowledge'
    key            TEXT,               -- NULL — запись без явного ключа (свободная заметка)
    value          TEXT    NOT NULL,
    source         TEXT    NOT NULL,   -- 'router' | 'manual'
    source_chat_id TEXT    REFERENCES chats (id) ON DELETE SET NULL,
    created_at     INTEGER NOT NULL,
    updated_at     INTEGER NOT NULL
);
CREATE INDEX owner_long_term_memory_owner ON owner_long_term_memory (owner, entry_type);
CREATE UNIQUE INDEX owner_long_term_memory_owner_key
    ON owner_long_term_memory (owner, entry_type, key)
    WHERE key IS NOT NULL;
```

Почему две таблицы, а не одна с полем «слой»: у слоёв разный первичный
контекст доступа (чат+задача против владельца) и разная политика удаления
при каскаде (`CASCADE` от чата против `SET NULL`) — общая таблица потребовала
бы nullable FK в обе стороны и условной логики каскада, что менее прозрачно,
чем две простые таблицы. `messages` не меняем: краткосрочный слой — это
существующий хвост истории, `WindowImpl` уже умеет его строить
(`window::assemble`), стратегия `memory_layers` переиспользует эту функцию
напрямую, а не копирует логику усечения окна.

Альтернатива, отклонённая: единая таблица `memory_entries(layer, scope_id, …)`
— упростила бы будущий четвёртый слой, но такого слоя не запрошено, а цена —
менее явные ограничения (`UNIQUE`/`CASCADE` пришлось бы делать частичными по
`layer`), что нарушает принцип «не проектировать под гипотетическое будущее».

### 2. Задача чата: колонка на `chats`, а не отдельная таблица задач

`chats` получает `active_task_id TEXT` (произвольная строка-идентификатор
задачи, генерируется клиентом или сервисом при первом обращении к рабочей
памяти без явного `task_id` — тогда используется `chat_id` как `task_id` по
умолчанию, чтобы рабочая память работала без обязательной ручной инициализации
задачи). Явное завершение задачи — операция маршрутизатора `{"op":"finish_task"}`
или HTTP `POST /v1/chats/{id}/memory/working/finish-task`: перед удалением
записей текущей `task_id` каждая запись с флагом `carry_forward` (доп. поле
операции `set`, по умолчанию `false`) переносится в
`owner_long_term_memory` как `entry_type = "knowledge"`, затем строки
`chat_working_memory` этой `task_id` удаляются, а `active_task_id` чата
получает новое значение (новый случайный идентификатор). Отдельной таблицы
задач не заводим: у задачи нет собственных атрибутов, кроме идентификатора и
факта активности, который и так виден как `chats.active_task_id`.

Альтернатива, отклонённая: таблица `chat_tasks(id, chat_id, status, …)` —
избыточна, пока задаче не нужно ничего, кроме идентификатора и границы
активности; добавить её позже — обратно совместимая миграция, если
понадобится.

### 3. Формат маршрутизатора: тот же принцип, что `facts.rs`, шире набор полей

Промпт маршрутизатора получает текущее состояние рабочей и долговременной
памяти (усечённое по лимитам) и новое сообщение пользователя, просит вернуть
JSON-массив операций вида:

```json
{"layer":"working","op":"set","key":"target_platform","value":"iOS 17+","reason":"…","carry_forward":false}
{"layer":"long_term","op":"set","entry_type":"decision","key":"auth_provider","value":"Clerk","reason":"…"}
{"layer":"working","op":"delete","key":"draft_title"}
{"layer":"working","op":"finish_task"}
```

Разбор — `parse_operations`, копия приёма `facts::parse_operations`: найти
первую `[` и последнюю `]`, `serde_json::from_str` внутри; неудача — `None`,
вызывающий код логирует и оставляет память без изменений (то же поведение,
что «отказ маршрутизатора не рушит ответ» в `facts.rs`, здесь оформлено как
явное требование спецификации, а не только тестом). Валидация после разбора,
до применения: `layer` — известное значение, `key` (кроме `finish_task`) —
непустая строка длиной в пределах `AGENTD_MEMORY_WORKING_KEY_MAX_CHARS` /
аналог для `long_term`, `value` — в пределах `AGENTD_MEMORY_*_VALUE_MAX_CHARS`,
`entry_type` для `long_term` — одно из `profile`/`decision`/`knowledge`.
Невалидная операция отбрасывается по одной, не весь пакет — так же, как
`facts.rs` не отбрасывает весь ответ модели из-за одной странной операции,
только эта операция размышленно отбрасывается независимо (в `facts.rs` весь
пакет применяется целиком, но там нет валидации по отдельности; здесь она
нужна явно по требованию задачи, поэтому расходится с `facts.rs` в этой
детали и добавляет цикл `for op in operations { validate; apply_or_log }`).
Вызов модели — тем же способом, что `facts::update_after_exchange`:
модель маршрутизатора берётся из `AGENTD_MEMORY_ROUTER_MODEL` (умолчание —
`state.config.model`, тот же приём, что `facts_model`), `reasoning`/`thinking`
отключены, `custom_response_mode = false`.

### 4. Приоритет ручной операции над автоматической в одном такте

Маршрутизатор вызывается и применяется ПОСЛЕ отправки ответа пользователю
(как `facts::update_after_exchange` — асинхронно после записи обмена), а
ручные HTTP-эндпоинты — синхронные запросы, поступающие в любой момент.
Гонка возможна только если клиент вызывает ручную запись того же ключа между
завершением обработки текущего сообщения и завершением маршрутизации того же
такта. Правило: `UPSERT ... updated_at = excluded.updated_at` только если
`excluded.updated_at >= updated_at` — то есть более поздняя по времени
операция побеждает, независимо от источника (`source` пишется, но не
участвует в сравнении). Так как маршрутизатор всегда стартует до того, как
клиент может успеть вызвать ручной эндпоинт по итогам ЭТОГО ЖЕ ответа (ручная
правка требует, чтобы клиент сначала увидел разбивку `context` в ответе,
которая приходит раньше запуска маршрутизатора — маршрутизация фоновая), на
практике ручная операция того же такта физически позже — упорядочение по
времени и есть содержательное правило «ручная побеждает при конфликте»,
описанное в спецификации. Тест закрепляет это конкретным сценарием: применить
операцию маршрутизатора с более ранним `updated_at`, затем ручную с более
поздним — итоговое значение от ручной.

Альтернатива, отклонённая: жёсткий приоритет «ручное всегда выигрывает»
отдельным флагом блокировки ключа — усложняет схему (нужен флаг «заморожен
для маршрутизатора») ради сценария, который сравнение по времени уже
покрывает корректно.

### 5. Стратегия `memory_layers`: переиспользование `window::assemble`

`agent-sever/src/memory.rs` реализует `ContextStrategyImpl::assemble`:
1. читает долговременную память владельца чата (лимит числа записей —
   `AGENTD_MEMORY_LONG_TERM_MAX_ENTRIES`, вытеснение — старые по `updated_at`
   отбрасываются первыми, оставляем самые свежие: долговременная память чаще
   всего актуальна последним обновлением, а не порядком создания);
2. читает рабочую память чата для `active_task_id` (лимит —
   `AGENTD_MEMORY_WORKING_MAX_ENTRIES`, то же правило вытеснения);
3. строит разделы `sections = [long_term_section, working_section]` в этом
   порядке (пропуская пустые — как `facts_section` пропускает пустой набор);
4. хвост краткосрочной памяти — прямой вызов
   `window::assemble(stored, effective_window_for_memory(...), new_message)`,
   где размер окна берётся из `AGENTD_MEMORY_SHORT_TERM_TAIL_MESSAGES` /
   `ChatSettings.memory_short_term_tail` (тот же принцип переопределения, что
   `effective_window` в `context.rs`, но отдельное поле, а не переиспользование
   `context_window_messages` — размер хвоста памяти концептуально свой параметр
   стратегии, а не общий с `sliding_window`, чтобы смена одной настройки не
   меняла поведение другой стратегии, если пользователь позже переключится).

`context: ContextDto` дополняется вариантом `for_memory_layers(...)` в
`dto.rs` с полями по каждому слою (число записей, число символов) и по
маршрутизатору (`applied_set`, `applied_update`, `applied_delete`,
`rejected`) — маршрутизатор ещё не отработал на момент сборки истории (он
фоновый, как обновление фактов), поэтому счётчики применённых операций
относятся к маршрутизации ПРЕДЫДУЩЕГО сообщения; это симметрично тому, как
`facts_updated` в `ContextDto::for_facts` сегодня заполняется вызывающим
кодом уже после факта обновления, а не внутри `assemble`.

### 6. Наблюдаемость и переменные окружения

Новые `AGENTD_MEMORY_*` (`agent-sever`):
- `AGENTD_MEMORY_ROUTER_ENABLED` (bool, умолчание `true`);
- `AGENTD_MEMORY_ROUTER_MODEL` (строка, умолчание — `state.config.model`);
- `AGENTD_MEMORY_SHORT_TERM_TAIL_MESSAGES` (u32, умолчание как у
  `AGENTD_CONTEXT_WINDOW_MESSAGES`);
- `AGENTD_MEMORY_WORKING_MAX_ENTRIES`, `AGENTD_MEMORY_WORKING_VALUE_MAX_CHARS`,
  `AGENTD_MEMORY_WORKING_KEY_MAX_CHARS`;
- `AGENTD_MEMORY_LONG_TERM_MAX_ENTRIES`, `AGENTD_MEMORY_LONG_TERM_VALUE_MAX_CHARS`,
  `AGENTD_MEMORY_LONG_TERM_KEY_MAX_CHARS`.

Разбор — той же функцией `parse_nonzero`/`parse_bool_named`, что остальные
лимиты `config.rs`. Поля-дублёры в `ChatSettings` (`agent-cli`):
`memory_router_enabled: Option<bool>`, `memory_short_term_tail: Option<u32>`,
`memory_working_max_entries: Option<u32>`, `memory_long_term_max_entries: Option<u32>`
— зеркалит существующий приём `context_strategy`/`context_window_messages`
(поле `Option<T>`, `effective_*` берёт настройку чата поверх умолчания
сервиса). Значения `*_key_max_chars`/`*_value_max_chars` только операторские
(без переопределения на чат) — они защищают хранилище от разрастания, а не
управляют качеством ответа, поэтому не тот параметр, который стоит открывать
клиенту.

### 7. Журналирование

Событие применения/отклонения операции пишется `tracing` со структурными
полями `layer`, `op`, `key`, `accepted`/`reject_reason`; поле со значением
(`value`) добавляется в запись только если `state.config.log_content`, тем
же способом, что уже решает `AGENTD_LOG_CONTENT` для прочего содержимого
(грепнуть по использованию `log_content` в текущем коде логирования обмена и
повторить приём, а не изобретать новый флаг).

## Risks / Trade-offs

- [Риск] Маршрутизатор — ещё один вызов модели на каждое сообщение,
  удваивает задержку до полного цикла (как уже верно для `facts.rs`) →
  Смягчение: маршрутизация фоновая, после отправки ответа пользователю (как
  `update_after_exchange`), не увеличивает время до первого ответа;
  `AGENTD_MEMORY_ROUTER_ENABLED=false` полностью выключает вызов.
- [Риск] `active_task_id = chat_id` по умолчанию означает, что без явного
  заведения задачи вся рабочая память чата ведёт себя как одна вечная задача
  → Смягчение: это осознанное умолчание ради работы «из коробки»; явная смена
  задачи — штатный путь для сценариев, где это важно, задокументирован в
  README и специфицирован отдельным требованием.
- [Риск] Правило «побеждает более позднее время» при конфликте требует
  согласованных часов процесса (нет распределённых часов, сервис один
  процесс с одной SQLite базой) → не проблема при текущей архитектуре
  (один инстанс `agentd`), но зафиксировать как допущение: масштабирование до
  нескольких инстансов `agentd` над одной базой потребует пересмотра этого
  правила.
- [Риск] Долговременная память растёт неограниченно по числу записей за
  пределами `AGENTD_MEMORY_LONG_TERM_MAX_ENTRIES` (лимит режет только то, что
  ПОДСТАВЛЯЕТСЯ в контекст, не то, что хранится) → Осознанный трейд-офф:
  очистка/архивация исторических записей вне области этого изменения; лимит
  подстановки достаточен для наблюдаемости и стоимости запроса.

## Migration Plan

1. `agent-cli/crates/core`: добавить `ContextStrategy::MemoryLayers` и новые
   поля `ChatSettings`, прогнать `cargo test`, запушить в `main`.
2. `agent-sever/migrations/0004_memory_layers.sql`: `ALTER TABLE chats ADD
   COLUMN active_task_id TEXT` (бэкофилл — `UPDATE chats SET active_task_id
   = id WHERE active_task_id IS NULL`, чтобы существующие чаты сразу
   получили рабочую задачу по умолчанию), затем `CREATE TABLE
   chat_working_memory`, `CREATE TABLE owner_long_term_memory` с индексами.
   Без правки существующих таблиц `messages`/`chat_facts`/`chat_summaries` —
   обратно совместимо, как и требует ограничение «схему БД менять только
   миграцией».
3. `agent-sever`: временно убрать `[patch]`, `cargo generate-lockfile`,
   `grep -A2 'name = "agentcore"' Cargo.lock` — убедиться, что зафиксирован
   коммит, вернуть `[patch]` для локальной разработки. Затем реализовать
   `memory.rs`, эндпоинты, `AGENTD_MEMORY_*`, тесты.
4. Откат: миграция не удаляет и не переименовывает существующие колонки —
   откат до предыдущей версии сервиса безопасен для старых данных (новые
   таблицы и колонка просто не используются старым бинарником); откат самой
   миграции (даунгрейд схемы) не предусмотрен, как и для миграций 0001–0003.
