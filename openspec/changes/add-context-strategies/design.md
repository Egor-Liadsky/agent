## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь важна текущая
механика сборки истории на сервисе.

Сегодня `POST /v1/chat` с `chat_id` идёт по одному пути
(`agent-sever/src/app.rs:553` `handle_chat_in_existing`): загрузить все
сообщения (`store::load_messages`), вызвать `compact_history`
(`app.rs:182`), проверить лимит (`check_context_limit`, `app.rs:124`),
прогнать конвейер, записать обмен `store::append_exchange`
(`store.rs:447`), вернуть блок `ContextDto { replaced_messages,
summary_built }`. Компактизация — единственный способ урезать историю, и
она всегда включена настройкой `summary_enabled`.

Ограничения, которые формируют решения:

- `ChatSettings` живёт в `agentcore` (`agent-cli/crates/core/src/config.rs`)
  и сериализуется в трёх местах: файл конфигурации клиента, JSON-колонка
  `chats.settings` в SQLite и тело `/v1`. Любое новое поле должно читаться
  из старых записей без ошибки.
- Ядро не знает ни про терминал, ни про SQLite: стратегии, которым нужны
  хранилище и вызовы модели, целиком принадлежат сервису; ядро несёт только
  типы настроек.
- `messages` уже имеет `UNIQUE (chat_id, seq)`, а ветвление вводит второе
  измерение — этот инвариант придётся менять миграцией.

## Goals / Non-Goals

**Goals:**

- Одна точка выбора стратегии и один интерфейс сборки истории, чтобы
  добавление пятой стратегии не трогало обработчик запроса.
- Ветвление, не копирующее сообщения: две ветки от одной точки делят общий
  префикс.
- Прогон сравнения, воспроизводимый без ручного набора 15 сообщений.

**Non-Goals:**

- Ветвление не становится полноценным деревом с переносом (rebase) и
  слиянием веток: только создание, переключение и чтение.
- Факты не извлекаются алгоритмически без модели (никаких регулярных
  выражений по тексту) и не векторизуются.
- Существующая стратегия `summary` в этом изменении не переписывается,
  только ставится за переключатель.

## Decisions

### Решение 1. Стратегия — перечисление в `ChatSettings`, а не флаги

`ContextStrategy` — `enum` из четырёх вариантов в `agentcore::config`, поле
`context_strategy: Option<ContextStrategy>` в `ChatSettings`
(`None` — «наследовать умолчание сервиса»), `#[serde(rename_all =
"snake_case")]`. Альтернатива — набор независимых булевых флагов
(`summary_enabled`, `window_enabled`, ...) — отвергнута: флаги допускают
бессмысленные сочетания («и окно, и пересказ, и факты»), а сравнить
стратегии между собой по логам становится нельзя. Существующий
`summary_enabled` остаётся: он выключает пересказ внутри стратегии
`summary`, но не выбирает стратегию.

Совместимость: отсутствующее поле в старом JSON чата и в старом
`config.toml` читается как `None` благодаря `#[serde(default)]`, то есть
как «умолчание сервиса», и старые развёртывания при незаданной
`AGENTD_CONTEXT_STRATEGY` получают `summary` — прежнее поведение.

### Решение 2. Стратегия — трейт со сборкой истории, вызываемый из одной точки

Вводится трейт уровня сервиса:

```rust
#[async_trait]
trait ContextStrategyImpl {
    async fn assemble(&self, ctx: &StrategyCtx<'_>) -> Assembled;
}
```

где `Assembled { history: Vec<Message>, observability: ContextDto }`.
Реализации — `summary.rs` (существующая логика, обёрнутая), `window.rs`,
`facts.rs`, `branch.rs`. `handle_chat_in_existing` выбирает реализацию по
действующей стратегии и вызывает `assemble` там, где сегодня вызывается
`compact_history`. Это тот же приём, что уже принят в проекте для
провайдеров (трейт `Agent`) и правил (стадии `pipeline.rs`): новое правило
добавляется реализацией, а не правкой вызывающего кода.

Ошибки внутри стратегии не заворачиваются в отказ пользователю без нужды:
как и сегодняшняя компактизация, стратегия при сбое вспомогательного
вызова возвращает историю подешевле и помечает это в наблюдаемости.

### Решение 3. Ветвление хранится указателями, а не копией сообщений

Схема (миграция `0003_context_strategies.sql`):

```sql
CREATE TABLE chat_branches (
    id           TEXT PRIMARY KEY,
    chat_id      TEXT NOT NULL REFERENCES chats (id) ON DELETE CASCADE,
    parent_id    TEXT REFERENCES chat_branches (id) ON DELETE CASCADE,
    fork_seq     INTEGER,              -- NULL у корневой ветки
    name         TEXT NOT NULL,
    created_at   INTEGER NOT NULL
);
```

`chats` получает `active_branch` (ссылка на `chat_branches.id`), `messages` —
`branch_id TEXT NOT NULL`. Инвариант `UNIQUE (chat_id, seq)` заменяется на
`UNIQUE (branch_id, seq)`: `seq` продолжает расти внутри ветки, а точка
ветвления задаётся `fork_seq` родителя. История активной ветки собирается
подъёмом по `parent_id` до корня: для каждой ветки в цепочке берутся её
сообщения с `seq <= fork_seq` дочерней ветки, для активной — все.

Альтернатива — копировать сообщения родителя в новую ветку при её создании —
отвергнута: удваивает хранение на каждой ветке и требует решать, что делать
с телеметрией скопированных сообщений; выигрыш был бы только в простоте
одного `SELECT`.

Альтернатива «ветка = новый чат со ссылкой на родителя» отвергнута:
ветки перестали бы быть видны как один диалог в списке чатов, а настройки
и факты пришлось бы копировать.

Миграция существующих данных: каждому чату создаётся корневая ветка
(`parent_id IS NULL`, `fork_seq IS NULL`), все его сообщения получают её
`branch_id`, `chats.active_branch` указывает на неё. Данные не теряются,
ручных шагов у оператора нет.

### Решение 4. Ветвление — стратегия и структура одновременно

Ветки хранятся и доступны всегда (эндпоинты и миграция от стратегии не
зависят), но на сборку истории влияют только при
`context_strategy = branching`: остальные стратегии работают внутри
активной ветки как со всей историей чата. Так стратегия остаётся сравнимой
с прочими на одном сценарии, и при этом переключение стратегии не приводит
к внезапной потере видимости веток.

Ограничение глубины: цепочка родителей не длиннее операторского потолка
(`AGENTD_MAX_BRANCH_DEPTH`, умолчание 8) — иначе одна сборка истории
превращается в неограниченное число запросов к БД.

### Решение 5. Факты обновляются после ответа пользователю, а не до

Порядок в стратегии `facts`: собрать историю «факты + хвост» → получить
основной ответ → записать обмен → обновить факты по последнему сообщению
пользователя. Обновление до ответа задержало бы каждый ответ на второй
вызов модели, а выигрыш был бы только на том же самом сообщении, которое и
так целиком есть в хвосте окна. Альтернатива «обновлять фоново, не дожидаясь
завершения» отвергнута: следующий запрос пользователя мог бы обогнать
обновление и увидеть устаревшие факты.

Промпт обновления просит модель вернуть JSON-массив операций
(`{"op":"set","key":...,"value":...}` / `{"op":"delete","key":...}`), а не
целый новый набор: так модель не может молча потерять факт, который просто
не упомянула. Неразбираемый ответ — не ошибка запроса: факты остаются
прежними, в наблюдаемость идёт признак `facts_updated = false`.

Хранение — таблица `chat_facts (chat_id, key, value, through_seq,
updated_at)` с первичным ключом `(chat_id, key)`: пары «ключ-значение»
нужны точечно правимыми через API, а JSON-колонка в `chats` заставила бы
переписывать весь документ на каждую правку и мешала бы потолку числа
фактов.

### Решение 6. Границы клиентских настроек по образцу существующих

`context_window_messages` и потолки фактов проверяются так же, как уже
проверяются `summary_keep_messages` и `summary_step_messages`
(`app.rs:389`): клиентское значение не больше операторского потолка и не
ноль, иначе `400` с отдельным кодом ошибки. Коды новые
(`context_strategy_invalid`, `context_strategy_not_allowed`,
`context_window_invalid`, `facts_limit_exceeded`), потому что различать
причины по тексту сообщения в этом проекте запрещено.

Проверка стратегии выполняется и на пути сохранения (`POST /v1/chats`,
`PATCH`), и на пути вызова: сохранить запрещённую стратегию, которая
сорвёт каждый следующий запрос, нельзя.

### Решение 7. Лимит контекста считается после сборки

`check_context_limit` остаётся, но получает `Assembled.history`. Это уже
так для компактизации (`app.rs:591`) — решение лишь распространяется на все
стратегии, поэтому окно и ветка тоже спасают чат от
`context_limit_exceeded`.

### Решение 8. Сравнение — детерминированный сценарий против поддельного провайдера плюс ручной прогон

Двухуровневая проверка:

1. Автоматический прогон в тестах сервиса (`src/tests.rs`) против `wiremock`:
   сценарий из 15 сообщений, у каждого ответа фиксированный текст. Он
   проверяет то, что можно проверить без живой модели: сколько сообщений и
   какие ушли провайдеру, сколько токенов по оценке, попала ли деталь из
   первого сообщения в запрос на пятнадцатом, независимы ли ветки. Это же
   даёт числа для колонок «расход токенов» и «устойчивость».
2. Ручной прогон против живой модели по описанной в отчёте команде — для
   колонки «качество ответа», которую поддельный провайдер не измеряет.

Сценарий (текст 15 сообщений и контрольные вопросы) лежит в
`agent-sever/tests/data/context-scenario.json`, чтобы оба уровня брали одни
и те же реплики. Отчёт — `agent-sever/docs/context-strategies-comparison.md`.

Альтернатива — измерять только вживую — отвергнута: числа не
воспроизводятся и отчёт нечем перепроверить после правки кода.

## Risks / Trade-offs

- Смена `UNIQUE (chat_id, seq)` на `UNIQUE (branch_id, seq)` — правка боевой
  таблицы сообщений → миграция пересоздаёт таблицу и переносит строки в
  одной транзакции, тест миграции наполняет БД по старой схеме и проверяет,
  что все сообщения читаются после обновления.
- Стратегия `facts` делает второй вызов модели на каждое сообщение
  пользователя, то есть может оказаться дороже пересказа на коротком чате →
  расход измеряется прогоном и попадает в отчёт; факты можно выключить
  переключением стратегии.
- Факты и пересказ — производное состояние, которое переживает переключение
  стратегии и может устареть → факты видимы и правимы вручную, пересказ
  остаётся привязан к `through_seq`, как сегодня.
- Ветвление плодит состояние в БД, которое клиент может не показать →
  корневая ветка есть всегда, чтение без указания ветки возвращает активную,
  так что старый клиент видит ровно одну линию диалога.
- Новые поля `ChatSettings` в ядре означают пуш `agent-cli` в `main` до
  проверки сервиса → порядок задач это учитывает; до пуша сервис собирается
  локально через `[patch]`.

## Migration Plan

1. Ядро (`agent-cli`): типы настроек, тесты чтения старого конфига и старого
   файла чата, пуш в `main`.
2. Сервис: миграция `0003`, стратегии, эндпоинты, конфигурация. Умолчание
   `AGENTD_CONTEXT_STRATEGY = summary` означает, что развёртывание без новых
   переменных ведёт себя как до изменения.
3. Клиент: настройка стратегии, экраны фактов и веток, подкоманды, README.
4. Прогон сценария и отчёт сравнения.

Откат: вернуть предыдущий образ сервиса можно только вместе с откатом
миграции — новая схема `messages` старому коду непонятна (он ждёт
`UNIQUE (chat_id, seq)` и не знает `branch_id`). Поэтому миграция
сопровождается обратной SQL-заготовкой, переносящей сообщения активной ветки
обратно в плоскую таблицу; сообщения неактивных веток при откате теряются, и
это записано в README как цена отката.
