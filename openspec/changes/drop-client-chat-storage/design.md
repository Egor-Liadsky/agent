## Context

Мотивация — в `proposal.md` («Why»), требования — в `specs/client-chats`,
`specs/client-transport` и `specs/chat-api`. Здесь только то, что нужно, чтобы
объяснить подход.

Текущее состояние:

- `crates/cli/src/chats.rs` — файловое хранилище (`ChatSession`, `save_chat`,
  `list_chats`, `delete_chat`, `context_block`, `last_activity_label`), файлы
  `~/.config/agentcli/chats/*.json`, идентификатор — наносекунды
  `SystemTime`.
- `crates/cli/src/tui.rs` (~2270 строк) — единственный потребитель хранилища.
  Работа с сетью уже асинхронна: запросы уходят в `tokio::spawn`, результат
  возвращается событием `ChatEvent` через `mpsc::unbounded_channel`, а на
  время ожидания у чата поднимается флаг `pending` со спиннером.
- `crates/client` (`agentclient`) умеет `ServerAgent::ask` (`POST /v1/chat`) и
  `list_models`; разбор ошибок сервиса — `parse_service_error` по коду
  состояния с извлечением `request_id` из тела или заголовка `x-request-id`.
- `crates/cli/src/agent.rs` — `CliAgent` диспетчеризует по
  `settings.provider`: облако в `ServerAgent`, `Provider::Ollama` — в
  локальный `OllamaAgent` из `agentcore`.
- На стороне `agentd` хранилище чатов уже реализовано (изменение
  `add-chat-storage-sqlite`, не заархивировано): эндпоинты `/v1/chats`,
  `POST /v1/chat` с `chat_id`, а в `store.rs` уже есть `append_exchange`,
  которая пишет пару «вопрос + ответ» одной транзакцией `BEGIN IMMEDIATE`.

Ограничения: `agentcore` не должен зависеть от терминала и остаётся общим для
клиента и сервиса; менять его в этом изменении нежелательно, потому что любая
правка ядра тянет пуш в `main` и обновление `Cargo.lock` сервиса.

## Goals / Non-Goals

**Goals:**

- Один источник истины по чатам — SQLite сервиса; клиент только отображает.
- Сохранить нынешний пользовательский опыт TUI: список слева, заголовок из
  первого сообщения, перенос контекста, локальный Ollama.
- Обойтись минимальным расширением серверного контракта — ровно один новый
  эндпоинт.
- Оставить `agentcore` и `agentupstream` нетронутыми, чтобы не потребовались
  пуш `agent-cli` в `main` и обновление `Cargo.lock` в `agent-sever`.

**Non-Goals:**

- Локальный кэш чатов и офлайн-режим TUI.
- Импорт старой локальной переписки на сервер.
- Стриминг ответа, поиск по чатам, вложения, синхронизация настроек клиента.
- Изменение схемы БД сервиса: новых таблиц и миграций нет.

## Decisions

### Решение 1: чаты Ollama сохраняются через новый эндпоинт записи обмена

Выбран вариант (в) из постановки: `agentd` получает
`POST /v1/chats/{id}/messages`, а клиент по-прежнему считает Ollama локально и
после ответа записывает готовый обмен в чат.

Почему не (а) «Ollama через `agentd`»: правок сервера он не требует, но
перекладывает локальную модель на сервис — запрос пользователя уходит с его
машины на хост `agentd`, адрес Ollama переезжает в `AGENTD_OLLAMA_URL`, и
локальный провайдер перестаёт быть локальным. Это меняет границу
ответственности, зафиксированную в конфигурации проекта («клиент ходит в
облако только через `agentd`, локальный Ollama — напрямую с машины
пользователя»).

Почему не (б) «чаты Ollama остаются в файлах»: остаются два хранилища, две
ветки в TUI и невыполненная цель изменения.

Цена решения (в): контракт `/v1` расширяется, работа делится на два
репозитория, а сервис получает эндпоинт, содержимое которого он не порождал —
значит, тексты в нём произвольные, и белый список моделей к ним неприменим
(см. `specs/chat-api`). Взамен локальный путь остаётся локальным: запрос к
модели не покидает машину, в сеть уходит только сохранение результата.

Последствия, названные прямо: `OllamaAgent` остаётся в зависимостях
`crates/cli`, адрес Ollama остаётся в конфиге клиента, но работать без
запущенного `agentd` TUI всё равно не может — список и история живут на
сервере. Без сервиса остаётся только `agentcli ask`.

### Решение 2: реализация эндпоинта поверх существующей `append_exchange`

Обработчик проверяет владельца, разбирает тело в две `NewMessage` (роли `user`
и `assistant`, телеметрия из `reply` в `MessageMeta`) и вызывает уже
существующую `store::append_exchange`. Транзакция, нумерация `seq` и
обновление `updated_at` достаются даром и совпадают с поведением
`POST /v1/chat` с `chat_id`.

Альтернатива — отдельная функция хранилища — дала бы второй способ писать в
`messages` и второй риск разъехаться по нумерации.

Форма тела повторяет ответ `POST /v1/chat` (`content`, `reasoning`, `model`,
`usage`, `timing`), чтобы клиент отправлял то, что только что получил, без
перекладывания полей.

### Решение 3: клиент чатов живёт в `agentclient`, ошибка «чат не найден» — тоже

CRUD чатов добавляется в `crates/client` рядом с `ServerAgent`: это уже
крейт-владелец знаний о контракте `/v1`, и `crates/cli` зависит от него.

`AgentError` в `agentcore` варианта «чат не найден» не имеет, а добавлять его
значит менять ядро и тянуть пуш в `main` с обновлением `Cargo.lock` сервиса
ради одного варианта перечисления. Поэтому `agentclient` заводит собственный
тип ошибки операций над чатами: вариант «чат не найден» для `404` с кодом
`chat_not_found`, остальные случаи — существующий `parse_service_error`,
результат которого переносится как есть. Причина по-прежнему различается
типом, а не текстом: `downcast_ref` до `AgentError` продолжает работать для
всех прочих кодов.

### Решение 4: чат создаётся лениво, при первой отправке

Сегодня TUI вставляет новый пустой чат прямо в список. С серверным хранилищем
это означало бы `POST /v1/chats` при каждом запуске и при каждом `Ctrl+N` —
список быстро зарастает пустыми чатами, которые пользователь не создавал
осознанно.

Поэтому новый чат — черновик в памяти: он виден в списке первым, у него есть
настройки, но на сервере его нет. Первая отправка выполняет `POST /v1/chats`
с накопленными настройками и заголовком по умолчанию, получает `id` и сразу
за ним шлёт `POST /v1/chat { chat_id, prompt }`. Правки настроек и
переименование до первой отправки остаются в памяти и уходят телом создания.

Цена: отправка в новом чате — два запроса подряд, и отказ второго оставляет на
сервере пустой чат. Это лучше, чем пустые чаты при каждом запуске;
альтернативу «создавать чат заранее и подчищать пустые при выходе» отвергаем
как молчаливое удаление данных.

### Решение 5: заголовок по первому сообщению остаётся, его делает клиент

Поведение «первые 40 символов первого сообщения» пользователю знакомо, а
сервер заголовки не выводит намеренно. Значит, после первого успешного обмена
клиент шлёт `PATCH /v1/chats/{id}` с заголовком, если тот всё ещё `Новый чат`.
Это один дополнительный запрос на чат — только на первом обмене.

Альтернативы: убрать осмысленные заголовки (список превращается в столбец
«Новый чат») или научить сервер выводить заголовок (правка контракта ради
косметики и навязывание правила всем клиентам).

### Решение 6: переписка читается целиком, страницами

`GET /v1/chats/{id}` умеет отдавать сообщения только от начала вперёд
(`after`, `limit`), «последних N» в контракте нет. Клиент при открытии чата
читает страницы подряд, пока `next_after` не станет `null`, и всё это время
показывает состояние ожидания тем же механизмом `pending`/спиннера.

Добавлять серверу обратную выборку (`before`) в этом изменении не будем: это
второе расширение контракта ради оптимизации, которую можно сделать отдельно,
когда появятся чаты, где полная загрузка ощутима.

Список чатов, наоборот, догружается по мере прокрутки: `GET /v1/chats` с
`limit` по умолчанию и `cursor` следующей страницы.

### Решение 7: перенос контекста собирается из прочитанного чата

`context_block` перестаёт быть функцией над локальным `ChatSession` и
становится сборкой блока из ответа `GET /v1/chats/{id}`: заголовок исходного
чата и его сообщения по возрастанию `seq`, прочитанные страницами до конца.
Форма блока («[Контекст из чата «…»]», «Вы:», «Агент:») не меняется, чтобы
модель видела привычный текст, а сам блок остаётся обычным сообщением
пользователя.

### Решение 8: старые локальные чаты удаляются без импорта

Импорт потребовал бы отдельной команды и того же нового эндпоинта, причём с
восстановлением ролей и телеметрии из файлов, у которых нет `seq`. Решено
(подтверждено пользователем) файлы не переносить, а удалять: клиент при старте
удаляет каталог чатов целиком и один раз печатает предупреждение с путём и
прямым указанием, что переписка потеряна безвозвратно.

Это разрушающая операция над пользовательскими данными, поэтому: удаляется
только каталог `chats` внутри директории конфигурации клиента, ничего выше по
дереву; неудача удаления не мешает работе, а печатается как сообщение;
предупреждение печатается ровно один раз, потому что второй раз каталога уже
нет.

### Решение 9: `chats.rs` остаётся, но только как форматирование и уборка

Из файла уходят `ChatSession` и все файловые операции чтения и записи чатов.
Остаются `last_activity_label` (чистое форматирование метки времени, нужно
списку) и однократное удаление устаревшего каталога из решения 8. Модуль не
удаляется целиком, чтобы `tui.rs` не разросся ещё сильнее.

Состояние чата в TUI (`id`, `title`, `settings`, загруженные сообщения,
`message_count`, признак «черновик», `updated_at`) переезжает в собственный тип
TUI: это уже не «сессия на диске», а вид на серверный чат.

### Решение 10: сеть в TUI — существующая схема `tokio::spawn` + `ChatEvent`

Новые операции (список чатов, страница истории, создание, переименование,
изменение настроек, удаление, запись обмена Ollama) выполняются теми же
`tokio::spawn` с отправкой результата событием в существующий канал. Новые
варианты `ChatEvent` несут либо данные, либо ошибку операции с `request_id`.
Экран ошибки — состояние панели, а не всплывающее сообщение, чтобы повтор был
осознанным действием пользователя.

Порядок работ между репозиториями: сначала эндпоинт в `agent-sever` с тестами
на `wiremock`-независимом уровне (`src/tests.rs`), затем клиент — иначе TUI
нечего звать. Пуш `agent-cli` в `main` и `cargo generate-lockfile` в
`agent-sever` не нужны: `agentcore` и `agentupstream` не меняются.

## Risks / Trade-offs

- **Без `agentd` клиент почти бесполезен: не открываются ни чаты, ни история,
  даже для локального Ollama** → Названо прямо в спецификации и README;
  состояние ошибки показывает адрес сервиса и способ повтора; `agentcli ask`
  и разовые вызовы продолжают работать.
- **Потеря старой переписки при обновлении** → Однократное явное
  предупреждение с путём до удаления; в README и в описании изменения
  помечено как **BREAKING**. Кому переписка нужна, тот успевает скопировать
  каталог до обновления, только если прочитает README заранее — это
  осознанная цена решения 8.
- **Смена `client_token` в конфиге меняет владельца** → Чаты привязаны к
  SHA-256-отпечатку токена, поэтому после смены токена список выглядит
  пустым, хотя данные на месте. Прежний список возвращается возвратом прежнего
  токена; клиент показывает пустой список, а не ошибку, и это надо описать в
  README. При пустом `AGENTD_CLIENT_TOKENS` аутентификации нет и все клиенты
  сервиса — один владелец: чаты видны всем, кто дотянулся до порта.
- **Открытие очень длинного чата тянет всю переписку страницами** → Загрузка
  асинхронная, со спиннером и без блокировки ввода; при необходимости позже
  добавляется обратная выборка на сервере (решение 6).
- **Отправка в новом чате — два запроса; отказ второго оставляет пустой чат**
  → Пустой чат виден в списке и удаляется обычным способом; повторная отправка
  идёт уже в созданный чат, а не создаёт второй.
- **Запись обмена Ollama может не дойти после успешного локального ответа** →
  Ответ остаётся на экране, ошибка записи показывается явно; повторная
  отправка того же обмена не выполняется автоматически, чтобы не задваивать
  сообщения.
- **Новый эндпоинт принимает произвольные тексты и имена моделей** → Он
  ограничен владельцем чата и общим ограничением размера тела; в журнал
  содержимое попадает только при `AGENTD_LOG_CONTENT=true`.

## Migration Plan

1. Выкатывается `agentd` с новым эндпоинтом: старые клиенты его не знают и
   продолжают работать.
2. Обновляется клиент. При первом запуске он удаляет каталог локальных чатов и
   печатает предупреждение.
3. Откат клиента к прежней версии возможен, но пустой: локальные файлы уже
   удалены, старый клиент начнёт с чистого списка. Откат сервиса возможен,
   пока не появились чаты, записанные новым эндпоинтом; сама схема БД не
   менялась, поэтому данные прежней версии читаются как есть.
