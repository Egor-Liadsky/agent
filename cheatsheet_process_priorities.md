# Шпаргалка: приоритеты Android-процессов, oom_adj_score и Low Memory Killer

Источник: конспект Android_Middle_Interview_Conspect.docx, раздел 1.1.2 «Процессы и приоритеты: foreground/visible/service/background/empty, low memory killer» и Q&A 1.3.

## 1. Базовое устройство процесса
- Каждое приложение по умолчанию работает в собственном Linux-процессе. [0009]
- Процесс создаётся при запуске первого компонента и живёт, пока система не решит его убить. Android почти никогда не завершает процессы «штатно»: приложение не выходит само, его убивает система под давлением памяти. [0009]

## 2. Как определяется приоритет
- Приоритет присваивается на основе самого важного активного компонента процесса. [0010]
- В терминах ядра это счётчик oom_adj_score: чем он выше, тем скорее процесс убьют. [0010]

## 3. Иерархия процессов (от наиболее к наименее защищённому)
| Процесс | Условие | Пример |
|---|---|---|
| Foreground | Активность на переднем плане (resumed), запущен foreground-сервис, выполняется BroadcastReceiver.onReceive() | Экран, с которым работает пользователь |
| Visible | Компонент виден, но не на переднем плане: activity в onPause (диалог поверх, мультиокно), bound-сервис, к которому привязана видимая activity | Activity под прозрачным диалогом |
| Service | Запущен started-сервис, не являющийся foreground | Фоновая синхронизация через Service |
| Cached (background/empty) | Нет активных компонентов; empty-процесс вообще не содержит компонентов и держится в памяти для ускорения следующего старта | Приложение после нажатия Home |

(строки таблицы: Foreground и Visible — [0010]; Service и Cached (background/empty) — [0011])

## 4. Low Memory Killer
- Освобождением памяти управляет Low Memory Killer (lmkd) — демон, который по сигналам давления памяти от ядра убивает процессы с наибольшим oom_adj_score. [0011]
- Low Memory Killer — один из патчей модифицированного ядра Linux в Android (наряду с Binder, Ashmem, wakelocks). [0004]

## 5. Порядок убийства и LRU
- Low Memory Killer убивает процессы по возрастанию важности: cached/empty → service → visible → foreground. [0040]
- Приоритет процесса определяется самым важным его компонентом: foreground — resumed activity, foreground-сервис или выполняющийся onReceive(); visible — activity между onPause и onStop; service — работающий started-сервис; всё остальное — cached LRU-список. [0040]
- Cached-процессы образуют LRU-список: чем дольше приложение не использовалось, тем выше в очереди на убийство. [0012]

## 6. Практические следствия
- Смерть процесса — нормальный сценарий, а не исключение: гарантированно вызываются только колбэки до onStop() + onSaveInstanceState(); onDestroy() при убийстве процесса не вызывается. [0012]
- Гарантированные колбэки перед возможным убийством — до onStop() и onSaveInstanceState() включительно; onDestroy() не гарантирован никогда, поэтому персистентные данные сохраняют не в onDestroy, а раньше. [0040]
- Пока выполняется onReceive() широковещательного приёмника, процесс считается foreground и не будет убит; сразу после возврата из onReceive() процесс может стать cached и погибнуть — поэтому долгую работу из ресивера передают в goAsync() или WorkManager. [0012]

## 7. Типичный вопрос на собеседовании
- «В каком порядке система прибивает процессы при нехватке памяти? Что важно помнить про onDestroy?» → cached/empty → service → visible → foreground; onDestroy() не гарантирован и при убийстве процесса не выполняется. [0040]

## Приоритеты в двух строках (для быстрого повторения)
`cached/empty → service → visible → foreground` — убивают именно в этом порядке [0040]; `oom_adj_score` — ядерный счётчик, чем выше, тем раньше убьют [0010]; `lmkd` — демон, который это делает по сигналам о давлении памяти [0011].
